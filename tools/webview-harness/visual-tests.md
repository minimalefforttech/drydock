# Webview Visual Tests

The visual check matrix for the browser harness in this directory. Checks run
against the REAL bundled panel (`dist/webview/main.js`) in a browser, a mock
host speaking the exact envelope protocol, and deterministic dummy fixtures
(no docker, no providers, no real folders). These checks validate UI wiring
and visuals; they cannot validate anything behind the host boundary (real
mounts, runtimes, toasts, the OS diff editor — those need guided manual
verification against a real VS Code window).

Run: `npm run bundle` (apps/vscode-extension) → start the `webview-harness`
launch config (port 8971) → drive with the preview tools. Scenario helpers on
`window.__harness.scenario`: `streamTurn(sessionId)`, `attention(sessionId,
reasons)`, `accessRequest(summary)`, `memoryCandidate(candidate)`.

Fixture cast: sessions `s-live` (active, codex, has plan-less transcript with
markdown+mermaid), `s-waiting` (active, claude), `s-ended` (resume target, has
plan docs), `s-failed`; tasks `t-1` (linked set-1 + s-live, lastWorkedAt),
`t-2` (bare); pending access requests `ar-rw` (read-write) and `ar-sens`
(read-only but `.env`, sensitive) + approved `ar-ok`; working set with
+12/−3, +40/−0, and an unrevertable delete.

## Notes

- Synthetic `.click()` on card wrappers does not reach inner handlers —
  dispatch bubbling `MouseEvent`s on the inner title/chip elements instead.
- `streamTurn` sequences must ride a high monotonic counter; panel dedupe on
  `lastSequence` is correct behavior, not a bug to work around.
- Background-tab timer throttling stretches both the panel's debounce/decay
  timers and `preview_eval` polling waits, so timing measurements taken across
  evals are unreliable — assert state transitions (in-page timestamped
  observers) rather than durations.
- The comment dock's narrow-stacking media query keys on viewport width,
  which the harness stage cannot shrink — dock stacking needs guided manual
  verification in a real window, same as the 420px/360px host-window checks.
- Real git sync (both conflict directions, the no-commit invariant), the
  native diff editor, Comments-API gutter threads, real submit→revision
  turns, and real `updateWorkspaceFolders`/window-reload behavior all need
  guided manual verification in a real VS Code window — none of this is
  observable from the browser harness.
